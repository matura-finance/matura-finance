---
title: Indexer & worker
description: How on-chain events become the fast read-model the API serves.
---

The read endpoints are fast because they don't hit the chain on every request — they read a **Postgres
projection** built by a separate-process **indexer worker** (`worker.ts`, run with
`pnpm --filter @matura/api worker:dev`). The HTTP API and the worker share one image; the role is
chosen by `SERVICE_ROLE`.

## How it works

- **Polls on the `finalized` tag.** The worker advances a cursor over finalized blocks, so projections
  reflect finality rather than reorg-prone head state.
- **Idempotent upserts under one advisory-locked transaction.** Event projection + cursor advance
  happen together, so re-processing a block is safe and the cursor can't diverge from the data.
- **Reorg safety.** A block-hash mismatch triggers a **full wipe + reindex** from the deployment block,
  rather than trusting a stale projection.
- **Confirmations are configurable** (`INDEXER_CONFIRMATIONS`): `0` works with an RPC that supports the
  `finalized` tag; a tagless RPC needs `> 0`.

## Operating it

- **Reindex from scratch:** `pnpm --filter @matura/api reindex` wipes projections and rebuilds from the
  deployment block.
- **Readiness:** during a first-boot reindex, `/health/ready` returns 503 — target `/health` for
  liveness probes.
- **Post-write lag:** after you submit a transaction, reads reflect it once the worker has indexed the
  finalized block — poll the projected state, not the cursor.

## Reconciliation

A local-only cross-stack harness (`apps/e2e-stack`) boots node + Postgres + worker + API, drives
optimize → execute → settle, and **reconciles events ↔ DB projections ↔ balances** to prove the
indexer and the chain agree.
